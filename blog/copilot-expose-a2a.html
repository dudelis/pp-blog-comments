Expose a Copilot Studio Agent as an A2A Endpoint

Expose a Copilot Studio Agent as an A2A Endpoint

Video Walkthrough
Below is the full walkthrough — this video shows you the architecture, setup, and how to connect agents across environments:

In this post, I’m going to show you how I expose a Copilot Studio agent as a reusable A2A endpoint.
This pattern lets you call a specialist agent — for example one that collects news or answers specific questions — from other agents, even if those agents live in different environments.

This isn’t something Copilot Studio supports natively today. Instead, we’ll build a secure proxy that:

  • accepts agent-to-agent (A2A) calls,
  • performs token exchange,
  • and calls the Copilot Studio agent runtime,
  • all without manual prompts or user login.

Let’s dive in.

Why This Matters

When you build a Copilot Studio agent, it lives in an environment. You can connect tools, create knowledge spaces, and even call other agents in the same environment.

But what happens when you want to:

  • call an agent from a different environment?
  • expose an agent as a capability in another part of your system?
  • enable an orchestrator or third party to use an agent’s logic?

There’s no built-in way to do this across environment boundaries.

You can register custom connectors or plugins, but those aren’t first-class agent interfaces. What we want is a true agent-to-agent integration, with authentication and access control.

The Dummy Agent We’re Exposing

Before configuring anything else, let’s define the target.

For this tutorial I have a simple “dummy” Copilot Studio agent that:

  • fetches current weather information,
  • answers questions about the weather,
  • behaves like a specialist capability, not a UI bot.

Imagine you're building a bigger orchestration agent — something like a corporate assistant. You want that assistant to delegate weather-related tasks to this Weather Agent, even if the assistant lives in a different environment or tenant.

That’s our use case.

App Registration and Permissions

To make this work securely, the first step is identity.

We create an Azure Entra ID app registration that serves as the identity for our proxy and the bridge between callers and the Copilot agent.

Expose the API

In the app registration:

  • Under Expose an API, set your application URI (usually api://<client-id>)
  • Add a scope like access_as_user — this becomes the scope that callers must request.
    This scope is what protects your proxy endpoint.

API Permissions

Next we add the delegated permission that allows the proxy to call Copilot Studio:

  • In API Permissions, look for Power Platform API
  • Add the delegated permission CopilotStudio.Copilots.Invoke
  • Grant admin consent

Finally, generate a client secret — our proxy will use this to authenticate when exchanging tokens.

This identity setup is essential: without it, we have no secure way to authorize calls or issue tokens.

The Azure Function Proxy

Now for the bridge itself.

I’ve built an Azure Function that implements A2A-style endpoints — these include agent metadata, a JSON-RPC endpoint, and the logic to forward requests to the Copilot runtime.

The Function:

  • accepts incoming agent-to-agent requests
  • verifies tokens using Easy Auth
  • performs on-behalf-of (OBO) token exchange
  • calls the Copilot Studio conversation endpoint
  • returns responses in A2A format

You can find the full implementation here:
https://github.com/dudelis/a2a-copilot-proxy

Environment Configuration

Once deployed, the Azure Function needs environment variables telling it:

  • which tenant it’s operating in
  • the client ID and secret of the app registration
  • where the Copilot agent runtime lives
  • and the public base URL of the Function

For Copilot Studio URLs, you extract:

  • the environment URL
  • the conversation endpoint
  • the bot ID

from the Web App channel configuration of the Copilot agent you want to expose.

Configuring Azure Function Authentication

To secure your Azure Function and prevent it from being exposed to anonymous users, you must configure authentication properly. This ensures that only authorized callers with valid tokens can access your proxy endpoint.

Enable App Service Authentication

Navigate to your Azure Function App in the Azure Portal:

  1. Go to Settings → Authentication

  2. Click Add identity provider

  3. Select Microsoft as the identity provider

  4. Configure the following settings:

    • App registration: Select your app registration we created earlier

  5. Under Restrict access:

    • Select Require authentication
    • For Unauthenticated requests: Choose Return HTTP 401 Unauthorized

Configure Allowed Token Audiences

This is a critical step that many developers miss. You need to explicitly configure which token audiences are allowed to call your Function.

In the Edit identity provider screen:

  1. Scroll down to Allowed token audiences
  2. Add the following audience value: api://{client-id} (where {client-id} is your app registration's client ID)
  3. Click Save

Without this configuration, the Function will reject incoming tokens even if they're properly scoped. The allowed token audience tells Azure to accept tokens that were requested for your specific API scope.

Why This Matters

By requiring authentication and specifying allowed token audiences:

  • Anonymous access is blocked — only callers with valid Entra ID tokens can reach your Function
  • Token validation is automatic — Azure validates the token signature, expiration, and audience before your code runs
  • Authorization is enforced — callers must have the correct scope (api://{client-id}/access_as_user) to get a valid token
  • Security is layered — even if someone discovers your Function URL, they can't call it without proper authentication

This authentication layer is essential for production deployments and ensures your Copilot agent proxy is properly secured.

Registering the Proxy as an A2A Agent

With the Function running and secured, the next step is to register it as an A2A agent inside another Copilot Studio agent.

This is done in:

Copilot Studio Agent → Agents → Add an agent → Connecto to an external agent → Agent2Agent

You provide:

  • the Function’s A2A JSON-RPC endpoint URL
  • authentication settings — using Microsoft Entra ID
  • the scope you created (api://<client-id>/access_as_user)

After you add the A2A agent, Copilot Studio generates a redirect URL. Copy this URL and add it to your app registration:

  • Go to Azure Entra ID → App registrations → your app → Authentication
  • Under Web, add the generated redirect URL
  • Save the configuration

This step is required for the OAuth flow to complete successfully.

Now, from the calling agent’s perspective, this looks and behaves like any other agent.

Under the hood, the call flows:

  1. Calling agent requests a token for the proxy
  2. Token is validated via Easy Auth
  3. Proxy exchanges token and calls Copilot Studio
  4. Copilot responds and proxy returns to caller

Testing the Integration

Once the calling agent and proxy are configured, test the flow by invoking the delegate agent.

You should see:

  • Authorization succeed
  • Proxy validate and forward calls
  • Copilot Studio agent respond normally
  • Responses arrive back in the caller

Common issues we fix at this stage include:

  • mismatched scopes / tokens
  • missing admin consent
  • incorrect Copilot runtime URLs

Summary

In this tutorial you learned how to:

  • expose a Copilot Studio agent through an Azure Function proxy
  • secure it with Azure Entra ID
  • register it as an A2A target
  • call it from a different Copilot agent

This pattern enables real cross-environment agent collaboration, which today isn’t supported natively in Copilot Studio.

Happy hacking! 🛠
