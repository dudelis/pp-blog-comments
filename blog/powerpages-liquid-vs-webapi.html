Liquid vs Web API in Power Pages: Data Loading Performance

Welcome to another Hack the Platform post! Today I’ll look at a very practical question:
How should you load data in Power Pages — using Liquid or the Web API?

Why Compare Liquid and Web API?

Both Liquid and the Power Pages Web API are common ways to load and render data. But I often see customers struggling with performance:

  • Entire datasets (sometimes tens of thousands of records) are loaded into the browser.
  • With Liquid, this means the page might take 20–30 seconds to render.
  • With Web API, the page loads faster, but data fetching shifts to the client.

So, which is better? Let me test it.

Test Setup

To make this concrete, I built a demo page that renders product cards. The test runs at three levels:

  • 200 items
  • 2,000 items
  • 10,000 items

The idea is not that anyone needs 10,000 products on a single screen — but I’ve seen real implementations where this happens. My goal is to show the trade-offs between the approaches.

I measured two things:

  • Liquid: since it’s server-side, I tracked Largest Contentful Paint (LCP), i.e., when the DOM is ready and the user can see the results.
  • Web API (JavaScript): The page loads instantly, but data is fetched and rendered asynchronously. I use a custom metric instead of LCP to measure when all data is fully loaded and rendered, as LCP does not account for the time taken by JavaScript to fetch and display dynamic content.

Best Practices

Here’s an important principle that applies to both Liquid and Web API:

Use Liquid with a server-side approach.
It doesn’t make sense to send 10,000 records to the browser. In real-world apps, users almost always search or filter. You can pass those search or filter values as URL parameters and let Liquid return a pre-filtered dataset. That way, you only send what the user actually needs — keeping load times fast while still leveraging server-side rendering.

The same rule applies to the Web API: even though I can fetch 10,000 items, it’s always better to load only what the user sees. If large datasets are required, I fetch them asynchronously in the background.

When to Use Liquid

  • Perfect for small datasets (like 200 items).
  • Good when you need server-side filtering before rendering.

When to Use Web API

  • Best for medium to large datasets.
  • The page loads fast, then data comes in asynchronously.
  • Load multiple datasets simultaneously, but avoid fetching everything at once.

Conclusion

  • At small scale (200 items) → Liquid and Web API are basically equal.
  • At medium scale (2,000 items) → Web API starts to shine.
  • At large scale (10,000 items) → Web API is the only realistic option.

The rule of thumb:

👉 Never load more data than the user actually needs.

By combining smart filtering, server-side queries, and asynchronous loading, you’ll avoid slow pages and keep the user experience smooth.
